# Lessons ledger

Production lessons learned the hard way. Each entry is a single-sentence
takeaway, traceable to the Beads task(s) that produced it, tagged for
retrieval, with the date it was first recorded.

## Entry grammar

One line per lesson, three HTML comments in a fixed order:

    - <text> <!-- sources: id1, id2 --> <!-- tags: gate, testing --> <!-- recorded: YYYY-MM-DD -->

**Line order is load-bearing.** `.claude/agents/grader.md` and
`.claude/rubrics/default.md` cite lessons by ordinal position ("lesson 1",
"lesson 2"), and `.claude/agents/orchestrator.md` cites "entry 1". Never sort,
group or re-section this file: doing so repoints those citations at different
lessons *silently* — nothing errors, and the citation still reads plausibly.
Scoping happens through tags, which leave line order untouched.

A field value containing `-->` would close its comment early and relocate
every later field on read-back, so `lessons.sh` rejects such input rather than
cleaning it. The arrow `->` is fine; `-->` is not.

## Tag vocabulary (closed)

Every entry carries at least one tag. Tags are a coarse retrieval filter, not
a taxonomy — an entry carries every tag a reader might plausibly filter on,
and when in doubt the tag goes on.

| Tag | Covers |
| --- | --- |
| `gate` | the QA gate and its machinery: approval binding, labels, hooks, Stop-time checks, the change-set tracker |
| `testing` | test design: oracles, fixtures, META-tests, what an assertion actually proves |
| `packaging` | install / uninstall / upgrade, the manifest, releases, vendored and generated artifacts |
| `agents` | agent prompts, spawning and delegation, model selection and ranking, subagent runtime behaviour |
| `evidence` | how you know a thing is true: measurement versus claim, silent-success failure modes, root cause |
| `process` | workflow and planning rules, the tracker, cost, and where a decision has to be written down |

The vocabulary is enforced by `TAG_VOCABULARY` in `.claude/scripts/lessons.sh`;
extending it means editing that list and this table together, and a test
asserts the two agree.

## Adding an entry

    bash .claude/scripts/lessons.sh add --stdin \
        --source <task-id> --tag <tag> [--tag <tag>]... <<'LESSON'
    <one sentence, framed as the rule for next time, not the story of this time>
    LESSON

**Use `--stdin` with a quoted heredoc.** Neither inline quote style is safe
for this corpus: single quotes protect the backticks lessons routinely contain
but end at the first apostrophe, and double quotes protect apostrophes but run
backticks as command substitution. Several entries below lost their
possessives to the single-quoted form — "the gate's own" became "the gate
own". **Do not repair them by re-adding a corrected version**: dedup matches on
normalized text, so a corrected re-add appends a duplicate instead of
replacing the damaged entry. Never hand-edit; the only legitimate hand-edit is
pruning entries that are no longer relevant.

## Reading

    lessons.sh list                            # the whole file, verbatim
    lessons.sh list --tag gate --tag testing   # OR-combined
    lessons.sh list --since 2026-07-01 --limit 10
    lessons.sh list --untagged                 # must always be empty

The orchestrator reads a recent slice during planning, the QA agent proposes
additions at epic close, and the grader (Phase A) receives the WHOLE ledger in
its packet — lessons are criteria-by-reference there, so filtering the
grader's copy would narrow the criteria it can apply. That is why `list` with
no flags prints the file verbatim, and why the grading-packet step in
`qa.md` must never pass a filter.

`design-reviewer.md` (v5 D2) joins the grader on the WHOLE-ledger side of this
split, for the identical reason: its DS8 criterion treats a lesson as a
criterion by reference, so a filtered packet would silently narrow what it
can cite. `designer.md` (v5 D1) scopes, like the orchestrator — but neither
of those two agents has a `Bash` tool (both are read-only-by-design or
write-one-file-only), so neither can invoke `lessons.sh` at all: the
design-reviewer opens this file directly and whole with its own `Read`; the
designer `Grep`s it for a `tags:` HTML comment naming the tag it wants (for
example, one carrying `agents`) against the closed vocabulary above, the
tool-appropriate equivalent of `list --tag`. The split itself is
the rule to apply to any FUTURE consumer, not the specific tool each one
happens to have: a role that CHECKS an artifact against every applicable
criterion needs the whole ledger, because a lesson it never saw is a
criterion it silently could not apply; a role that PLANS or COMPOSES
benefits from a relevant slice instead, because the whole file would
otherwise crowd out the artifact actually in front of it.

A filtered `list` call also prints a JSON accounting line to stderr — total
ledger size, how many matched, how many `--limit` cut, and why — so a scoped
read that matches nothing prints `"matched":0` rather than looking identical
to a call that silently returned less than it should have. Stdout is
unaffected: every existing scoped-read consumer keeps parsing exactly the
bytes it already parsed.

Treat this as the institutional memory the plugin runs against, not a static
reference doc.
