## Cross-cutting principles

All v4 principles carry forward unchanged: no automatic paid runs; prompts are suggestions, mechanics are guarantees; the change-set-hash-bound `qa-approved` record (with independent reviewer identity) is the only release credential; evidence-before-fix; day-zero model adoption per role class; doc style per CLAUDE.md; per-phase closeout with landing-the-plane; AskUserQuestion after 2–3 stuck attempts. Additions for this release:

1. **Effort default is `max` everywhere, per the recorded V0 verdict.** Every new agent, script, and command inherits it. Ultracode is re-evaluated only if a changelog entry changes the workflow-layer behavior — if you see one, note it in LESSONS.md and the Beads meta-task rather than switching unilaterally.
2. **Upgrades are first-class.** From this release on, "installs cleanly" means both fresh installs and in-place upgrades from the previous minor version, and both are proven by executed tests, not inspection.
3. **User customizations are never silently clobbered.** Where an upgrade must replace a file the operator may have edited, write the new version alongside (`.new`) and report, or merge non-destructively — never overwrite in place without a backup and a line in the upgrade readout.

## Phase U0 — v3.5 → v4 installer upgrade path (the priority)

v4 added many shipped files (workflow-denylist.sh, gate-baseline v2, worktree approval resolution, model-roles, reviewer templates and rubrics, CODEX_SETUP.md, revised qa-gate.sh and hooks). A project that installed v3.5 must reach the same end state as a fresh v4 install without losing its own customizations. The installer's history demands rigor here: it silently dropped `grader.md` for two releases before glob-copy landed — that class of failure is what this phase eliminates permanently.

- **Detection:** add v3.x→v4 upgrade signals alongside the existing v2 detection: `.claude-plugin/plugin.json` with a `3.x` version; absence of v4 artifacts (`.claude/model-roles`, `workflow-denylist.sh`, rubrics/reviewer templates, `docs/CODEX_SETUP.md` equivalents in the installed tree). Auto-detect triggers upgrade mode; `--upgrade` forces it.
- **Behavior:** back up the existing `.claude/` to `.claude-v3-backup-<timestamp>/` before writing anything. Preserve operator-owned files (`CLAUDE.md`, `LESSONS.md`, `.claude/model-ranking`, `.claude/model-roles` if present, any customized rubrics — detect customization by hash against the shipped v3.5 originals; modified files get the `.new`-alongside treatment). Merge `settings.json` per the existing pattern: workflow-owned keys replaced, operator keys preserved. Rewrite `.mcp.json` entries to the `${CLAUDE_PROJECT_DIR:-.}` form and re-verify both manifests agree.
- **Record-format compatibility:** pre-v4 approval records lack `reviewed_by` and `worktree=` fields. The gate must treat them as historical — valid for already-closed tasks, never re-blocking closed work — while requiring the full v4 format for any new approval. Add an explicit test for a v3.5-era closed task surviving the upgrade untouched.
- **Packaging parity (absorbs `bzy`):** a manifest-driven parity test — every file the repo ships is enumerated in a generated manifest, and a post-install assertion verifies each is present in the target. This runs for fresh installs AND upgrades, in CI, at zero API cost. The grader.md failure mode becomes structurally impossible.
- **Tests:** an L2 upgrade spec that builds a genuine v3.5 fixture from the actual `v3.5.0` git tag (git archive or worktree into a temp project), seeds operator customizations (a custom CLAUDE.md line, a custom env key in settings, one modified rubric), runs `install.sh` non-interactively (`--mode=2`), and asserts: parity manifest satisfied; customizations preserved; modified rubric got `.new` treatment with a readout line; backup directory exists; `.mcp.json` in the diagnostics-clean form; a second run is idempotent (no changes, no duplicate backups). Then a fresh-vs-upgraded equivalence check: diff the upgraded tree against a fresh v4 install, asserting the only differences are the preserved operator files.
- **Acceptance:** the v3.5-tag fixture upgrades cleanly end-to-end; a post-upgrade gate smoke (enter → approve with a bound record → release) passes in the upgraded project; the upgrade readout lists preserved / replaced / `.new` files explicitly. `install.ps1` receives the same changes with line-by-line parity inspection; actual Windows execution remains a documented caveat, not a silent claim.

## Phase U2 — Worktree cleanup sweeper (absorbs `prm`)

The plugin leaves stale worktrees and scratch copies behind. Build the sweeper mechanically and conservatively:

- A `worktree-sweep.sh` helper plus SessionEnd wiring. A worktree is a removal candidate only when ALL hold: its branch is merged or pushed (verify via `git fetch --prune` + merged/remote checks), its associated Beads task is closed, and it exceeds an age threshold. Dry-run is the default; `--apply` is explicit. Un-pushed or dirty work is never touched — tie the check into the landing-the-plane contract.
- Scratchpad denylist (`prm`): tracked scratch locations (temp clones, mutation worktrees, agent scratch dirs) join the shared workflow denylist so they never enter QA change sets, and the sweeper knows them as always-safe-to-list candidates.
- Tests: L1 with stubbed `git`/`bd` covering candidate selection, age threshold, dry-run vs apply, and cleanup-on-failure. META-TEST: a fixture worktree with an un-pushed commit must never appear as removable — mutate the safety check and the assertion must fail.

## Phase U3 — Context-gathering loop

Make "gather until exhaustion" mechanical rather than aspirational:

- A coverage ledger (sources visited: files, symbols, docs, tickets, sibling repos) and a frontier queue (discovered-but-unvisited), maintained by a small harness the orchestrator and reviewer lanes call. Termination is structural: frontier empty, or a hard cap (frontier depth, source count) hit — with `stopped_by` recorded, reusing the V2 review-template convention.
- Every exhaustive-mode delegation carries the same mandatory `risk_threshold` and `stop_condition` fields as reviews; the harness rejects requests missing them. This is the mechanical answer to diligence-as-infinite-loop.
- Wire it into the orchestrator's pre-decomposition step and offer it to the reviewer lane. Caps live in one config file.
- Tests: L1/L3 on the ledger/frontier harness (dedup, termination on empty frontier, termination on cap with correct `stopped_by`, rejection of uncapped requests). META-TEST: mutate the cap check so the frontier can grow unbounded — the termination assertion must fail.

## Phase U5 — Staging e2e QA loop with injected auth

Post-deploy verification against a live staging environment, abstract across auth providers, strictly manual.

- **Provider contract:** a project-supplied executable at `.claude/staging-auth` emitting strict JSON `{token, baseUrl, expires_at}`. The plugin never implements a provider; it documents reference implementations — Clerk first (JWT template mint and M2M token paths, with the billing note that M2M usage is metered), plus a generic OIDC client-credentials example.
- **Safety rails, mechanical:** a deny-pattern config for production-looking `baseUrl`/audience values — the command refuses to run against anything matching it; short-TTL guidance in the docs; the token is passed to the session environment, never written to tracked files.
- **The command:** `qa-on-staging` (Claude-invokable), manual-only with the standard cost estimate and confirmation. It runs API-level checks derived from the change's SPEC and, when the operator has a headless Playwright MCP configured, drives browser verification for frontend changes — optional, never a required dependency. Durable output: committed spec files as the regression artifact, plus a Beads comment with results; a chat transcript is not a test suite.
- **Reviewer-lane synergy:** when the Codex lane is active, the reviewer may drive `qa-on-staging` as part of its review — same manual gating, same caps.
- Tests: L1 provider-contract validation (malformed JSON, missing fields, expired token rejected), the production-pattern refusal, and an L2 flow test with a stubbed provider plus stubbed HTTP server. Live staging runs are dev-cycle manual validations only, recorded with cost in the closeout notes.
